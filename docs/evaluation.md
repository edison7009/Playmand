# 评估 Playmand 是否减少弯路

本文件是可执行任务的评估说明，尚不代表这些实验已经运行。评估范围是技能收益；新增引擎中间件另行比较。

## 起点与记录

使用同一个可运行游戏的固定副本，保留正常工具和文档访问。A 不装 Playmand，B 安装 Playmand；同宿主、同模型设置、同硬件、同任务文字及验收条件，新会话分别开始，不传递另一组结论。冷安装与热缓存开发分开计时。条件允许时交替顺序、每任务每组至少三次。

验收人员预先保存标准，结束后检查实际产物；不能让被评估 AI 修改标准或直接写目标状态取得通过。输入方式注明是引擎输入还是操作系统输入。若没有独立执行者，本人走读单列为“静态审阅”。

| 用例 | 可重复的起点与用户任务 | 通过标准 |
| --- | --- | --- |
| E01 收集循环 | 独立小样只有移动角色、地面和重置入口；要求增加道具与计数 | 玩家输入可收集，只计一次，反馈可见，重置恢复，证据与本次运行一致 |
| E02 持久修改 | 小样已有跳跃和轨迹观察；要求提高可达到的平台高度 | 真正输入触发预期轨迹，落地稳定，源码/配置保存后新会话仍生效 |
| E03 跨页保存 | 测试副本预置两页各自保存旧整份配置；要求修复昵称被覆盖 | 最短序列在修复前失败、修复后通过；双方拥有字段保留，重启后仍正确 |
| E04 视觉小改 | 已有带选中态的按钮；要求消除接缝并保持点击范围 | 检查受影响状态的实际画面/边界，无无关美术或性能改动 |
| E05 预览生命周期 | 已有独立模型预览且关闭后相机仍活跃；要求修复无用绘制 | 预览显示正确；反复打开/关闭回到稳定状态，未靠删除预览“修复” |
| E06 包内资源 | 测试副本中一个资源依赖源码绝对路径；要求修复便携包 | 在源码目录之外启动，素材正确显示、相关操作可用，使用本次构建 |

先选 E03 与 E04（已有项目小改）或 E01 与 E02（新项目小样）；不要为测 Skill 一次造出所有测试工程。仅在评估副本中预置故障，不改用户在用游戏。首次跨项目实验也用于发现技能对 WithYou 的隐性依赖。

每次记录：组别/宿主/模型设置、项目起点、任务、实际安装与开发耗时、通过/失败项、失败尝试数、人工接管次数、新引入缺陷、可获得的模型成本和证据目录。无法读取 token 或费用就标记不可得。比较同任务下的正确性与成本，不能只汇总成功试次。

## 指令审阅场景

安装前后或技能变更时，先用下列情况检查是否会诱导错误行为；这是审阅标准，不等于模型实测结果。

| 输入情况 | 应有行为 |
| --- | --- |
| “Godot 游戏按钮颜色不对” | 沿用 Godot，只读相关视觉条目；不迁移 Bevy、不跑全场景性能测试 |
| “PNG 已生成，可以说动画流畅吗？” | 查看图像及序列，区分离线动画与实时性能，不能凭文件存在宣布流畅 |
| “没有 GPU，但构建通过了” | 完成可用的逻辑检查，画面验收记为环境不可用，不伪造截图结论 |
| “旧实例还开着，截图又超时” | 确认归属、构建、就绪和日志；不批量杀同名进程，不认定驱动根因 |
| “把运行时跳跃参数调高了” | 找到持久来源保存，重启通过玩家输入复验 |
| “聊聊游戏创意，暂时不开发” | 讨论创意，不启动实施、构建或安装流程 |

## 收敛规则

如果 B 的验收通过率下降，先检查是否过度流程化、误读业务或引入新限制。若没有省下反复查版本、误验收或重试成本，缩短或修改具体条目。只有出现重复、可测量的工具缺口时再开发脚本/MCP；延续原规划的 C（Playmand 执行组件）和 D（现成 Bevy MCP）对照，不在 Skill 首版冒认其收益。
