# App 界面升级：给已有应用换新界面

验证来源：一次真实的升级。对象是一个 Tauri + React 桌面应用的模型管理和账号管理两页（中间是卡片，右侧是目录），先和用户在预览页里来回调了大约十五轮，再移植进应用自己的组件。在应用副本上，它自己的类型检查、lint、格式检查和全部测试（202 个文件、3249 项）都通过了，最后以补丁加交接说明的形式交付。[预览套件](../../../../skills/playmand/examples/app-ui-preview/index.html)和 [`brand_colour.py`](../../../../skills/playmand/scripts/brand_colour.py) 都来自这次工作。

用户想让已有应用的界面更好看时用本页：卡片、列表、侧边栏、空状态、按钮。设计方法是 Playmand 的（先看图、对比、检查真实结果）；代码跟随应用自己的技术栈。React、Vue、Svelte 或纯 CSS 都保持原样，不会为此改用 Rust。

## 先读懂应用

动手画之前，先找出：

- **这一屏背后的组件**、它们的 props，以及会出现的每一种状态：加载中、空、忙碌、失败、禁用、未安装、被隐私开关遮挡。只照顾正常状态的改版，一用就会出问题。
- **主题**：颜色变量（常见的是 `--bg-surface-rgb` 这类令牌）、圆角、字体、深色和浅色。用这些来设计，不要另起一套颜色。
- **应用自己的规矩**，通常写在给 agent 或贡献者的说明里，比如“不做自定义悬停提示”“保持系统默认鼠标指针”。预览里也要遵守。
- **这一屏用到的素材**：图标、logo。它们就是美术，不要重画。
- **碰到这些组件的测试**，以及测试靠什么找元素（标签、角色、组件类型、类名）。改之前先跑一遍，之后出现的失败才能确定是自己造成的。

## 先看图，在预览页里定稿

从目标画面开始：用户截一张自己喜欢的界面，就是最好的需求。然后在动应用之前，先做一个**独立的 HTML 预览页**：

- 把应用的主题变量复制进去，用应用真实的图标和名称（仓库里常常就带着目录文件），深色和浅色并排显示。
- 当前设计和新设计放在一起，每一轮都是对比。
- 方向还没定时，把**三到四个版本**并排给用户挑，再细化选中的那一版。看图挑选很快，看文字描述挑选很慢。
- 每轮只改一两处，并说明改了什么。会有很多小轮次（高度、重叠多少、悬停移动多少、哪些标签要留）；在预览里改一次几秒钟，在应用里改一次要几分钟。
- 每一轮都要能刷新看到最新效果（迭代时绕过模块缓存），告诉用户好了之前自己先截图看过。

[预览套件](../../../../skills/playmand/examples/app-ui-preview/index.html)是一个起点：顶部是主题变量，底部是示例数据，中间一组卡片、侧边一叠卡片。用 `python3 -m http.server` 在它的文件夹里启动服务，这样才能读取图标取色。

## 验证过的做法

**从图标取品牌色。** 给每个厂商的卡片配上它自己的颜色，从它的图标里读：取最主要的饱和色相（白、黑、灰像素不参与），把明度和饱和度收进一个白字在所有品牌上都看得清的区间，再继续加深，直到白字对比度达到 3:1（WCAG 大字标准）。黑白 logo 用中性的石板灰卡片。不需要维护配色表，远程列表里新增的条目也会自动上色。在应用里，这一步在浏览器里读取图标像素完成（[`brand.js`](../../../../skills/playmand/examples/app-ui-preview/brand.js)）；`scripts/brand_colour.py icon.png icon.svg` 在命令行里给出同样的颜色，可以用于设计说明或静态配色表。SVG 按文件里声明的颜色计数，而不是按覆盖面积，所以多色 SVG logo 的结果可能和浏览器里不同。

**彩色卡片上的可读性。** 卡片一旦带上品牌色，在灰底上好用的规则就会失效：

- 数字保持正文颜色，含义交给进度条（绿、黄、红）。绿色卡片上的绿色数字会消失。
- 危险值变成白字红底的小徽章，在任何品牌色上都清楚，包括红色和橙色卡片。
- 透明底上的单色 logo，在同色卡片上画成白色，否则会消失（红色标志放在红色卡片上）。多色 logo 和自带底色方块的 logo 保持原色。
- 黑白 logo 跟随主题：深色主题白色，浅色主题黑色。
- 每一轮都检查两种主题；深色里浓郁的底色，在浅色里可能发闷，浅色要用更淡的底色。

**目录用堆叠卡片。** 侧边“可添加的厂商”列表：整宽的品牌色卡片，每张卡片的下沿（7px）压在下一张下面；悬停的卡片只上抽一点（3px），因为下面藏着的部分没有内容，抽多了什么也露不出来。最后一张没有隐藏的下沿。“添加”是这叠卡片里的第一张，用浅色，这样既醒目又不脱离这叠卡片。整张卡片是主操作；次要操作（打开官网、取消、切换地区）是叠在上面的独立按钮，绝不做成按钮里套按钮。

**堆叠卡片上的状态。** 忙碌：一道光扫过，显示倒计时，出现一个小的取消按钮。未安装：卡片变灰并写明。可选项（地区、服务商）：卡片上的一个小胶囊，里面保留应用原来的切换按钮。

**用户要求保留的文字。** 用户会注意到少了的信息：改版去掉字段标签，或者把两个字段挤到一行，多半会被要求加回来。可以先给更简洁的版本，但标签要随时能加回来。

## 移植进应用

- 在应用的**副本**里改（或用户同意的分支）。在副本里先提交一个基线，这样补丁只包含这次的改动，用户原来未提交的改动也算在基线里。
- 只改外观，不改行为：props、处理函数、无障碍名称、禁用和忙碌规则都不变。样式写进样式表或应用的工具类，用主题变量；做一个小的共享组件（比如堆叠卡片）比把同样的标记复制到两页里更好。
- 测试依赖的结构要保留（比如每行一个带标签的 `section`、测试读取的类名），只在改动是有意为之的地方更新测试，并说明原因。
- 按仓库自己的配置格式化：先确认仓库的格式化配置已经在，再运行格式化工具；保持原来的行尾（有些仓库用 CRLF）；交付前检查 diff 里有没有纯格式化造成的噪音。
- 跑应用自己的检查：类型检查、lint、格式检查、全部测试。
- 真实组件至少渲染一次（做一个小的查看页，用示例数据在两种主题下挂载它们），和用户确认过的预览对比。

## 交付

应用在别的仓库时，交付**补丁和交接说明**，不直接在那边提交。说明里写清楚：每个区域改了什么、有意的行为差异、应用命令、测试结果、真实组件的截图，以及没能验证的部分（各平台真实桌面窗口、不支持 `color-mix()` 的旧版 WebView）。对照仓库当前状态试应用补丁（`git apply --check`）；如果期间已经有人应用了旧版本，就补一个增量补丁，而不是重新出一个完整补丁。

## 踩过的坑

- 颜色写成 `hsl(220 9% 30%)`，标记里出现了“%”，一个检查卡片上不能出现假“0%”的测试因此失败。颜色要写成 `rgb()`。
- 浅黄色品牌生成的卡片太亮，白字看不清，加了对比度加深这一步才解决。
- 在复制仓库的格式化配置之前就运行了格式化，项目里写在一行的代码被折成了多行；之后用正确配置再跑一次也恢复不回来。
- 一个脚本用 LF 重写文件，CRLF 仓库里的文件每一行都变成了改动。
- 堆叠卡片上的链接按钮调用了 `event.stopPropagation()`，测试直接调用 `onClick()` 不传事件，于是失败；同级按钮本来就不需要它。
