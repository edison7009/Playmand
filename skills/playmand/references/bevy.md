# Rust / Bevy 项目工作方式

这是来自 Windows Bevy 项目的经验，不是强制新游戏选型。下述字段及 API 都应按项目锁定版本核实。

## 版本与最短运行路径

- 先看 Cargo.toml、Cargo.lock、rust-toolchain 文件及项目指令。确认实际 crate 版本、feature、目标平台和构建配置；多成员工作区先确定正确 package。
- Rust 已安装不代表 Windows 链接器、SDK、GPU 或辅助插件可用。先使用项目已有最小构建/运行入口证明所需能力，不默认升级全局工具链。
- 已有锁文件时使用项目约定的锁定构建。典型命令是 `cargo check --locked`、`cargo test --locked`、`cargo build --release --locked`，选择项目需要的组合；遵守项目另行要求的 release 测试。不要为纯文档变化重编译游戏。
- API 报错先查已安装的对应 crate 源码、版本化文档或同版本示例，随后做最小编译验证。不要为了匹配记忆中的接口升级依赖。
- 工具或 MCP 的公开功能列表只能作为候选。检查与当前 Bevy 版本及 Windows 的兼容性，实测本次所需的输入、查询或捕获再依赖它。

## ECS、调度与资产

- 确认事件生产和消费、文本编辑、动画、变换传播、UI 布局与读取结果的时机；一个组件刚写入不保证最终布局已更新。优先修正具体顺序，不堆等待帧数。
- 场景实例准备、动画/骨骼可用、目标相机渲染、截图回读完成是不同阶段。依据版本实际提供的事件/状态等待；如果只能用有限轮询，记录超时条件与限制。
- 根 GLB 可共享时先加载根资产，再复用场景和动画句柄；是否发生重复解码以当前版本的日志/测量为准。独立实例、材质修改和共享资源的边界明确。
- 仅在值实际改变时写 Transform、Visibility、UI 样式或材质，避免无效变化传播；在任务涉及相应热点时处理，不借此全仓重构。
- 显示层、主相机、倒影相机、UI 和独立预览分别核对。一个实体在两个 pass 显示，不一定是生成了两个实体。
- 更新循环中避免同步文件/网络读取、反复资产构建及无界任务；为新增轮询提供停止/取消路径。不要通过阻塞渲染线程等待异步资源。

## 保存与打包

运行时 ECS 修改通常只影响当前会话。找到真实来源（Rust 常量、配置、场景或资产），保存后重启，不能宣称任意运行时修改都能自动反写源码。

沿用项目资源清单及打包脚本，检查新增资产是否同时进入加载和分发路径。从包目录设置工作目录启动，并在离开源码目录的场景验证。开发控制入口按项目机制隔离，玩家包默认不开放开发控制接口。不要照抄参考项目的检查环境变量或复制其私有素材。
