# Playmand

让下一次游戏开发复用已验证的方法，少重复摸索。使用宿主现有的文件、命令、观察及输入工具；本技能不提供游戏引擎、MCP 服务或自动安装能力。

## 开始时确定本次闭环

1. 读取适用的项目指令（如 AGENTS.md、CLAUDE.md）、当前运行入口与最近验证记录。确认工作目录、未提交改动、引擎实际版本以及本次涉及的文件；不默认全仓审查。
2. 用几句话说明本次范围、关键假设和玩家可观察的通过标准。现有游戏沿用技术栈；新项目已有用户选择就遵循它。影响玩法、目标平台或交付物的歧义先澄清，常规实现自行完成。
3. 先找已有构建、启动、输入、状态查询、截图和打包入口，只确认本次需要的能力。缺少某项时先检查宿主或项目可用工具，再补最小开发态接口；不因没有 MCP 重建整套平台，不凭本文件假设任何工具已经存在。

新游戏先打通一条短的玩家循环：开始 → 操作 → 反馈 → 完成或失败 → 重试。先让核心操作可玩，再扩大场景和内容。占位素材明确标注；玩法、反馈与美术分别验收，数量多不等于完成度高。

## 实施与反馈循环

1. **复现并定位。** Bug 先找到失败状态或最短操作序列；无法复现时保留观察条件。区分源码问题、资源问题、启动错版本及环境干扰。API 不符先查锁定版本的文档、示例或源码，不连续猜字段。
2. **只改必要部分。** 沿用项目结构与风格。状态、时间和生命周期修复用能暴露原问题的回归检查；简单视觉调整优先查看实际画面，避免只断言自己写入的常量。
3. **运行并等待实际完成。** 记录本次构建和会话，等待场景、资产及目标输出就绪。命令退出、任务完成和截图写完各有实际依据；请求已接受不等于成功。超时先查日志及状态，不盲目增加等待或重启多个实例。
4. **操作并观察。** 流程验收经过玩家输入路径；调试注入可用于准备初始场景，但不能直接写最终计数或胜利状态来证明玩法完成。读取操作前后状态，检查实际图像；连续动作检查时间序列。
5. **保存并复验。** 临时修改运行时状态后，要保存到项目声明的源码、配置或资产来源，再重启检查。对存档改动使用隔离数据目录，并验证保存/重载；不要用测试覆盖玩家存档。
6. **完成针对性检查。** 遵守项目已有必做检查，增加本次变化对应的检查即可。无新改动、失败或疑点时不重复全量测试。交付可执行游戏时，从分发目录启动并验证相关流程。

每次失败后先说明新证据与下一项要排除的原因，再更改或重试。相同条件下重复失败且没有新证据时，停止原样重试，缩小复现或报告具体缺失能力；继续完成不依赖该阻碍的工作。不得为了通过测试悄悄削减已认可的玩法、画质或验收标准。

## 完成时交付

向用户先说明可玩结果与改动，给出实际启动入口和证据位置。区分通过、失败、未执行和环境不可用；有关键验证缺口时说明交付状态，不能宣称完全验收。视觉看过哪些状态、输入经过哪一层、性能测了什么，要与证据一致。

有新经验时更新项目已有验证/交接记录，只保存最短复现与有效结论。按 [经验沉淀](references/learning.md) 判断是否适合加入共享技能；不把游戏的业务选择或本机路径变成所有项目的规则。
